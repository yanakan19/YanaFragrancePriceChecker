# Ingestion audit — why retailer listing counts are low

Module 1.1. Audited 8 Aug 2026 against `a443cfd`. Every figure here was
measured from the repo or from `data/strategy-memory.json`, not estimated.

**Headline: the problem is not tuning. Eight major UK retailers have never
been successfully harvested even once, and their absence has been silent.**

### Correction to earlier reporting

Status updates in this project have repeatedly quoted per-retailer counts
including "Boots 9, Selfridges 7, John Lewis 8". Those are **fixture counts —
invented test data** generated by `scripts/catalogue-fixtures.ts` on 31 Jul and
1 Aug. They are not real listings and never were. Any figure derived from them,
including the "15 retailers" implied by the raw file list, overstated real
coverage. The honest number of retailers supplying real prices is **7**.

The guard that keeps this data off the site works correctly
(`build-demo-catalogue.ts:338`, *"Invented data never reaches the app,
whatever else happens."*). Nothing wrong has been published. But nothing
reported the failure either.

## Three distinct failure classes

Consolidated from `data/strategy-memory.json` (79 records across 6 retrieval
strategies). Formatted as successes/attempts.

### Class 1 — Hard blocked. No free route exists.

| Retailer | Total across all strategies |
|---|---|
| boots | 0/18 |
| harvey-nichols | 0/20 |
| notino-uk | 0/20 |
| selfridges | 0/20 |
| superdrug | 0/20 |
| the-fragrance-shop | 0/20 |
| the-perfume-shop | 0/20 |
| john-lewis | 0/17 |
| kayali / lush / zara | 0/5 each |

Every strategy — plain fetch, browser headers, sitemap discovery, search page,
homepage probe — has failed every single attempt. These are the same shops that
returned 403 in the 1 Aug spike. **This is not a code defect.** The retrieval
layer is working; these shops refuse datacentre IPs at the edge, before any
markup is served.

There are exactly three honest ways out, and none of them is a code fix:

1. **Affiliate feeds.** Boots, Superdrug, LOOKFANTASTIC, The Perfume Shop and
   several others run Awin programmes. A feed is sanctioned, free, richer than
   a crawl, and monetises. **Strongly recommended** — it is the same move that
   solved this problem on 3 Aug for Fragrance Click and MyBeauty Boutique.
2. **The residential proxy.** `APIFY_PROXY_PASSWORD` is not set, so
   `--allow-metered` is currently a no-op. Setting it would route these shops
   through Apify at roughly $8/GB. Works, costs real money, and the
   `MAX_PROXIED_REQUESTS_PER_RUN` ceiling already exists to contain it.
3. **Say so in the UI.** List them honestly as "not yet available" rather than
   holding fixtures indefinitely.

### Class 2 — Reachable but unreadable. This one is a real code defect.

| Retailer | Discovery | Harvest outcome |
|---|---|---|
| escentual | sitemap-discovery **1/1 success** | 0 priced listings |
| scentstore | sitemap-discovery **1/1 success** | 0 priced listings |

These shops answer. Discovery succeeds. The walk fetches a page and extracts
nothing. That points squarely at `parseListings` — either the shop publishes no
JSON-LD, or publishes it in a shape the parser does not read (microdata, or
prices embedded in a `__NEXT_DATA__` / inline JSON blob).

This is the highest-value pure-code fix available, and it is genuinely
fixable. It needs one CI diagnostic run to capture the actual markup, because
this container cannot reach retailer domains (see Constraints).

### Class 3 — Working, but likely under-harvested

allbeauty (116), lookfantastic (54), bellavita-luxury (24), oud-arabian (171)
succeed via sitemap discovery but hold far less than their real catalogues.
Two candidate causes, both measurable:

- Discovery is capped at **12 sitemap fetches** (`crawlViaSitemap` calls
  `discover(options, 12)`). A large retailer nests product sitemaps behind an
  index; 12 fetches can expire before reaching the fragrance aisle.
- The page budget is `--max=60` with 30% reserved for refreshing known prices,
  so a shop gains at most ~42 new products per run.

Note the budget is **not** currently the binding constraint for the shops whose
run records survive: stored records show `pagesFetched` of 2–4, far below 60.
Discovery, not budget, is what starves them. Raising `--max` alone would change
nothing.

## The observability defect

This is the finding that matters most, because it is why the above went
unnoticed for a week.

Two silent paths hide total retailer failure:

1. **`scripts/catalogue-harvest.ts:144`** — `if (dryRun || withPrice.length === 0) continue;`
   A retailer that yields nothing is skipped without writing. Its file keeps
   whatever it held before — in eight cases, fixtures from 31 July — forever.
   Nothing records "this shop has never worked".
2. **`scripts/build-demo-catalogue.ts:338`** — `if (snapshot.source !== 'live') continue;`
   Correct behaviour, but a bare `continue`. Unlike the `skippedShops` list
   below it, which *is* reported, this one drops eight retailers with no
   output at all.

A run where every one of eight retailers fails completely currently looks
identical to a healthy run. That is the same class of bug as the gzipped
sitemap issue from the bug log: **an empty result and a broken result must
never look the same.**

| # | Action | Class | Effort | Needs a decision |

| 2 | Quarantine the eight fixture files so a future regression cannot ship invented prices | Safety | Small | No |
| 3 | CI diagnostic run to capture Escentual/ScentStore markup, then extend `parseListings` | 2 | Medium | No |
| 4 | Raise discovery budget, measure, tune | 3 | Medium | No |
| 5 | Apply to Awin for Boots, Superdrug, LOOKFANTASTIC, The Perfume Shop et al | 1 | Ongoing | **Yes** |
| 6 | Decide: set `APIFY_PROXY_PASSWORD`, or list Class 1 shops as unavailable | 1 | Small | **Yes** |

Items 1–4 are unambiguous and can proceed. Items 5–6 are yours.

## Constraints discovered during the audit

This container **cannot reach retailer domains** — the environment's network
policy denies CONNECT (verified: 403 from the gateway for boots.com,
selfridges.com, escentual.com). That is why harvests work in GitHub Actions and
not locally. Any diagnostic requiring live markup must run in CI via
`workflow_dispatch` and be read from the run logs. Offline analysis — stored
snapshots, strategy memory, the demo build — runs fine locally, and produced
every finding above.
